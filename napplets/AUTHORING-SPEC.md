# Napplet Authoring Specification

This document defines how napplets in this repository are designed, created,
built, verified, loaded, and prepared for publication. It covers napplet-owned
code only. Shell and runtime implementation belongs elsewhere.

Napplet tooling and NIP-5D remain alpha. Before changing protocol-facing code,
compare this document with the current [napplet getting-started guide],
[NIP-5D status], and [NAP domain specifications]. Normative protocol language
belongs to those upstream specifications; repository-specific requirements are
identified below.

## 1. Product boundary

A napplet is a small, single-purpose web application hosted in a sandboxed
iframe. It renders product UI and asks its shell to perform mediated work. It
does not own the user's signer, relay pool, persistence, or host navigation.

Every napplet in this monorepo MUST:

- live at `napplets/<dTag>/`;
- do one narrow product job;
- build independently;
- emit `dist/index.html`;
- communicate through injected NAP domains;
- declare only domains it directly calls;
- tolerate optional domains being absent;
- clean up subscriptions and resource handles when no longer needed;
- pass type checking, build verification, and conformance checks before release.

Runtime packages, host services, service workers, registry generators, and
shell UI MUST NOT be placed under `napplets/`.

## 2. Sandbox contract

The host loads napplets using `sandbox="allow-scripts"` without
`allow-same-origin`. Napplet code MUST assume an opaque origin.

Napplet code MUST NOT use:

- `window.nostr` or direct signer APIs;
- private keys;
- `localStorage`, `sessionStorage`, IndexedDB, Cache Storage, or service workers;
- direct `fetch`, `WebSocket`, or `EventSource` access for product data;
- `window.parent` DOM access;
- cookies or host globals;
- external runtime assets that require ambient network access.

Use shell-mediated domains instead: `storage` for persistence, `resource` or
`upload` for bytes, `outbox` or `relay` for Nostr traffic, `identity` for the
active account, `link` for external navigation, and `intent`/`inc` for napplet
coordination.

The shell authenticates the iframe through `MessageEvent.source`, not data sent
by the napplet. Napplet code MUST NOT invent or send a caller identity. Treat
incoming intent/INC payloads as application input and validate their shape.

## 3. Required project layout

```text
napplets/<dTag>/
├── .napplet/
│   └── config.json          # CLI-owned deployment metadata when initialized
├── src/
│   └── main.ts
├── index.html
├── package.json
├── tsconfig.json
├── vite.config.ts
└── dist/                    # generated, never hand-edited
    ├── index.html
    └── .nip5a-manifest.json # generated by official Vite plugin
```

`dist/` may contain more artifacts when external assets are enabled. Built-in
packaging copies the complete tree. Prefer single-file mode because `srcdoc`
loading otherwise requires correct base-URL handling for every relative asset.

## 4. Create and initialize

Official greenfield path requires Node.js 20+ and current standalone `napplet`
CLI:

```sh
napplet create my-napplet
cd my-napplet
napplet init --name my-napplet \
  --title "My Napplet" \
  --description "One precise job." \
  --archetype item:napplet:item/open
```

Move generated project under `napplets/my-napplet/` before adding it to this
workspace. Preserve scaffold scripts and `.napplet/config.json`; do not create
a second deployment-metadata source in application code.

The stable `dTag`/CLI name SHOULD equal directory name. It MUST remain stable
after publication because configuration, package identity, cache keys, ACLs,
and external coordinates depend on it.

## 5. Repository metadata

Built-in discovery additionally requires `package.json#napplet`:

```json
{
  "name": "@platform/my-napplet",
  "private": true,
  "type": "module",
  "napplet": {
    "dTag": "my-napplet",
    "title": "My Napplet",
    "requires": ["identity", "storage", "outbox"],
    "archetypes": [
      { "slug": "item", "convention": "napplet:item/open" }
    ]
  }
}
```

This repository metadata feeds local built-in discovery. Portable publication
metadata remains `.napplet/config.json` plus generated NIP-5D/NIP-5A manifest
data. Values shared by both surfaces MUST agree.

Package name MUST match `@platform/*-napplet`; root build scripts use that
pattern to build napplets before shell packaging.

## 6. Dependencies and imports

Napplet application code SHOULD import typed domain wrappers from
`@napplet/sdk`:

```ts
import { identity, outbox, storage } from "@napplet/sdk";
```

Direct `window.napplet.<domain>` access is valid for no-build applications, but
this TypeScript monorepo SHOULD use SDK named exports. Napplet code MUST NOT
import `@napplet/shim`; runtime owns namespace injection before application code
runs. Import public package entry points only.

Applesauce, relay pools, account managers, and signers belong to shell/runtime
implementation here. A napplet MUST NOT create its own `EventStore`, relay pool,
or signer to bypass NAP mediation.

## 7. Capability selection

`requires` is least-capability declaration, not list of everything shell might
support. Add domain only when production code directly invokes it.

Common choices:

- `identity`: active public key, profile-related identity calls, account change.
- `storage`: instance- or napplet-scoped persistent state.
- `outbox`: outbox-aware Nostr query, subscription, signing, and publication.
- `relay`: explicit shell-mediated relay operations when outbox routing is not
  correct product behavior.
- `resource`: policy-controlled remote metadata or bytes.
- `upload`: shell-mediated Blossom upload.
- `config`: host-managed settings and schema.
- `theme`: initial theme and theme updates.
- `intent`: discover or open another archetype handler.
- `inc`: exact-topic inter-napplet messages.
- `link`: confirmed external navigation.

Hard capability absent: render clear non-destructive error and stop affected
flow. Optional capability absent: degrade gracefully. Never invent a discovery
API. Use SDK/domain presence as defined by current package surface.

Keep these declarations synchronized:

1. `package.json#napplet.requires` for this repository's built-in registry.
2. `nip5aManifest({ requires })` in `vite.config.ts` for portable manifest tags.
3. Actual domain imports and calls in source.

## 8. Vite build

Use official build plugin and single-file mode:

```ts
import { nip5aManifest } from "@napplet/vite-plugin";
import { defineConfig } from "vite";

export default defineConfig({
  base: "./",
  plugins: [
    nip5aManifest({
      nappletType: "my-napplet",
      title: "My Napplet",
      description: "One precise job.",
      requires: ["identity", "storage", "outbox"],
      artifactMode: "single-file"
    })
  ]
});
```

Expected scripts:

```json
{
  "scripts": {
    "dev": "vite build --watch",
    "build": "vite build",
    "type-check": "tsc --noEmit",
    "verify": "pnpm type-check && pnpm build",
    "test:conformance": "pnpm build && napplet-conformance ./dist"
  }
}
```

Plugin generates `dist/.nip5a-manifest.json`, per-file SHA-256 values, aggregate
hash, `path` tags, aggregate `x` tag, and capability metadata. Production
publishing signs through `napplet deploy`; napplet source MUST NOT contain a
production signing key.

For this monorepo, built-in registry generation independently hashes every file
in `dist/`. Source presence does not make app loadable; `dist/index.html` must
exist when shell dev/build begins.

## 9. HTML and assets

`index.html` MUST contain UTF-8 charset, viewport metadata, meaningful title,
description, and one application entry point. Build output MUST be self-contained
in single-file mode. Do not hand-edit generated HTML.

This repository's current loader obtains capability data from registry metadata;
portable tooling obtains it from manifest `requires` tags. A
`<meta name="napplet-requires">` marker may aid artifact inspection but MUST NOT
replace generated manifest declarations.

Avoid root-relative asset URLs. Multi-file builds MUST use paths resolvable from
artifact directory and MUST survive host base paths such as `/shell/`.

## 10. Application lifecycle

Runtimes inject domain namespace before napplet code executes. Current official
SDK guidance does not require application code to call `shell.ready()` or
`shell.supports()`; SDK calls delegate to injected domains and report missing
domains. Follow current package API rather than older examples.

Application startup SHOULD:

1. Resolve required DOM elements.
2. Verify hard domain availability using current SDK contract.
3. Load identity, configuration, theme, and stored state concurrently where safe.
4. Render useful pending and failure states.
5. Start subscriptions only after handlers exist.
6. Close every subscription and revoke every resource handle during teardown.

Do not treat raw Vite preview as runtime proof. Without compatible shell, keys,
storage, relay policy, and injected NAP domains do not exist.

## 11. Nostr reads and writes

Prefer `outbox` for social data because shell owns NIP-65 routing and shared
event infrastructure. Use `relay` only when product explicitly requires chosen
relay semantics.

Publish unsigned event templates through shell:

```ts
const result = await outbox.publish({
  kind: 1,
  content: "Hello from a napplet",
  tags: [],
  created_at: Math.floor(Date.now() / 1000)
});

if (!result.ok) throw new Error(result.error ?? "Publish failed");
```

Napplet MUST NOT sign locally, choose user's private key, or fan out directly.
Validate filters and payloads before requests. Bound result sizes and timeouts.
Close live subscription handles when view or napplet ends.

## 12. Storage, configuration, and secrets

Persist app state through NAP-STORAGE. Choose instance scope for one mounted
instance and broader scope only when product semantics require sharing. Keys
should be stable, namespaced by feature, and versioned when stored shape changes.

NAP-CONFIG schema MUST use plugin-supported JSON Schema subset. Do not use
unsupported `$ref` or `pattern`. Secret fields MUST use supported secret marker
and MUST NOT define defaults. Never put credentials, private keys, tokens, or
deployment secrets in source, HTML, package metadata, or generated registry.

## 13. Theme and accessible UI

Use NAP-THEME when available. Apply background and text tokens to full document,
not only inner card. React to theme updates. Provide readable fallback tokens.

UI MUST support keyboard use, visible focus, semantic controls, labeled forms,
status/error announcements, reduced motion, narrow iframe sizes, and long or
localized text. Motion in this repository MUST use GSAP when technically
possible and respect reduced-motion preference.

## 14. Archetypes, intents, and INC

Convention identity is exact queryless URI:

```text
napplet:<archetype>/<action>
```

Manifest example:

```json
{ "slug": "item", "convention": "napplet:item/open" }
```

Do not infer Nostr kind or payload schema from archetype name. Document payload
schema beside feature, validate incoming payloads, and version convention when
breaking semantics change.

Use structured intent result to distinguish request success from `handled`.
Receiving delivery is separate push carrying runtime-attested sender. Never
accept sender from payload. INC subscriptions and handler lookup use exact
queryless convention identity.

## 15. Verification gates

Run from repository root:

```sh
pnpm check
pnpm build
pnpm test
pnpm test:conformance
pnpm test:browser
```

For one napplet:

```sh
pnpm --filter @platform/my-napplet type-check
pnpm --filter @platform/my-napplet build
pnpm exec napplet-conformance napplets/my-napplet/dist
```

Inspect built artifact and generated manifest, not source alone:

```sh
test -f napplets/my-napplet/dist/index.html
rg '"d"|"requires"|"path"|"x"' napplets/my-napplet/dist/.nip5a-manifest.json
rg 'window\.nostr|localStorage|sessionStorage|indexedDB|fetch\(|WebSocket|EventSource' napplets/my-napplet/src
```

Forbidden-surface scan should return no production-code matches unless current
NAP specification explicitly documents exception. Verify `requires` exactly
matches calls, hashes match bytes, root-relative assets are absent, runtime can
mount under non-root base, missing optional domains degrade, and teardown closes
resources.

## 16. Runtime smoke test

Run through compatible shell, not raw Vite page. Official standalone flow uses
Paja:

```sh
napplet paja -- pnpm vite --host 127.0.0.1
```

For this monorepo, `pnpm dev` first builds all `@platform/*-napplet` workspaces,
starts their watch builds, then starts shell. Confirm:

- napplet appears in `/napplets.dev.json`;
- artifact resolves at `/napplets.dev/<dTag>/index.html`;
- shell installs and opens it through sandboxed window manager;
- identity/theme/config states render;
- each declared domain flow works;
- missing optional domain shows designed fallback;
- reload uses new development artifact;
- close removes subscriptions, object URLs, and session state.

## 17. Publication

Before external publication, run all gates and inspect generated manifest.
`napplet deploy` owns production signing, Blossom upload, and relay publication.
Record published `dTag`, aggregate hash, artifact locations, conventions, package
versions, and verification evidence in release notes.

Built-in inclusion and external publication are separate distribution paths but
must converge on same artifact and capability contract. Built-in status grants
no extra runtime API.

## 18. Completion checklist

- [ ] Source located at `napplets/<dTag>/`.
- [ ] One narrow product purpose documented.
- [ ] Stable directory name, `dTag`, CLI name, and built-in name agree.
- [ ] `.napplet/config.json` initialized for portable deployment.
- [ ] `package.json#napplet` present for built-in discovery.
- [ ] Only current `@napplet/sdk` public imports used.
- [ ] No direct signer, relay pool, storage, or ambient network access.
- [ ] `requires` matches direct domain calls exactly across all metadata.
- [ ] Archetypes use exact queryless conventions.
- [ ] `dist/index.html` produced, preferably single-file.
- [ ] `.nip5a-manifest.json` generated and inspected.
- [ ] Type check, build, conformance, repository unit, and browser tests pass.
- [ ] Shell smoke test completed with teardown and missing-domain cases.
- [ ] Release report records evidence and remaining gaps.
